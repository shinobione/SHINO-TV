# SHINO // TV V0.8 Mission 2 — internal protocol and ownership review

**Decision before implementation:** no fundamental contradiction prevents a compile-only, deny-all preparse seam. There is **no approval** for the proposed authenticated media protocol, native route, or verifier. This review is internal engineering analysis and does not replace independent security review.

## HTTP carriage and RFC fit

The proposed `POST /api/v2/bridge/media/{operation}/{tx} HTTP/1.1` puts operation and transaction in the request target, so an owner can classify and later authorize them before consuming a body. The 40-byte binary record repeats operation, epoch and transaction. A future Gate 2 must check exact byte agreement after authenticated body integrity; the request target alone is an untrusted declaration. The proposed denial-only prototype reserves raw and once-percent-decoded media namespace occurrences, including malformed media requests, before calling the legacy parser. Its preparse is deliberately more conservative than the target grammar and never creates a media request handler.

The proposed [RFC 9421](https://www.rfc-editor.org/rfc/rfc9421.html) base covers `@method`, `@request-target`, `@authority`, `content-type`, `content-length` and `content-digest`. `@request-target` is the actual HTTP/1.1 request-line target. `@authority` is the authority of the target URI, usually conveyed by Host in HTTP/1.1; treating a supplied Host string as authority requires a uniquely parsed Host, origin-form constraint, configured authority policy, port/case handling, and independent canonicalization tests. This profile cannot be reused behind a proxy or another HTTP version without review. RFC 9421 signs the digest **declaration**; it does not establish that received bytes match. The [RFC 9530](https://www.rfc-editor.org/rfc/rfc9530.html) `Content-Digest` must be recomputed over the exact complete body before any media state change. `Content-Length` framing, trailing bytes and pipelining remain a separate ingress responsibility.

The Mission 1 host regex accepts only one fixed serialization of `Signature-Input`, `Signature` and `Content-Digest`. That can be a narrow application admission policy, but it is not a general [RFC 8941](https://www.rfc-editor.org/rfc/rfc8941.html) parser: RFC 8941 requires support for at least 256 Inner List members and 256 parameters. Its dictionary and parameter parsing ordinarily retain the last duplicate key; this profile instead needs an explicit raw duplicate rejection before an interpretation can lose that evidence. Whitespace, combined fields, parameter order, string escaping and byte-sequence canonicalization must receive independent parser differential tests. [RFC 9651](https://www.rfc-editor.org/rfc/rfc9651.html) now obsoletes RFC 8941. The owner must decide whether the production profile intentionally pins the older syntax or updates the normative reference and vectors. This is an interoperability and review decision, not a reason to activate a permissive parser.

ECDSA-P256-SHA256 fixed host vectors validate signature mechanics in Node, not key custody, authentic HTTP component extraction, native constant-time verification, or challenge issuance. A fresh boot epoch, unpredictable single-use per-principal challenge, role/operation binding, revocation, bounded slots and failure behavior are still unimplemented. A 64-bit random epoch alone is not a proof of never repeating an epoch. The existing Basic/Digest browser fallback, cookies, `track_key`, CRC and image hash confer no media authorization. No production key or private secret is present in this Mission 2 prototype.

## Minimal native ownership seam

The pinned `ESP8266WebServerTemplate::handleClient()` in Core 3.1.2 owns `_server.accept()` and `_currentClient`. Its `_parseRequest()` uses an allocating `String` for the unbounded request line and subsequently parses ordinary headers/body before a handler. A second acceptor, second socket reader, `server.on()` or an `addHook()` cannot prove the required pre-body boundary. The smallest candidate is an **isolated overlay of that same template**: accept once, read at most 64 available first-line bytes per call into a fixed 131-byte member slot, terminate after a 130-byte wire cap or a wrap-safe absolute 2,000 ms deadline, deny reserved media, then give the exact line to a minimally changed `_parseRequest()` while leaving every subsequent client byte unread. The existing owner then handles legacy headers, body, handler, keep-alive and closure.

The overlay adds no route and is compiled only with `SHINO_V08_PREPARSE_EXPERIMENT=1` in `experiments/v08_preparse`; its default environment is the stock baseline. Installed Core files and `firmware/` are unchanged. A fixed stack decode of percent escapes prevents a once-decoded media target from falling into legacy routing. The direct source harness executes the transformed pinned methods with fake clients. Its one acceptor, no reread and pipeline observations are source-path evidence, not TCP, browser or hardware evidence.

## Incompatibilities and residual risks

The 130-byte first-line bound intentionally rejects some legacy requests that the stock parser formerly accepted. Thus legacy parity is established only for the bounded ordinary routes exercised; byte-for-byte acceptance parity for every historical request is impossible under the new global cap. The stock parser still allocates unbounded header Strings and can block for ordinary POST bodies. The first-line deadline does not bound legacy header/body processing, native callback time, TCP buffering, memory fragmentation or watchdog interval. A true all-ingress denial-of-service hardening would need a larger separately reviewed change.

The prototype closes a media candidate without reading its headers or body. It does not send a complete HTTP error response, verify a signature, authenticate a principal, or implement Gate 2. Delayed pipeline bytes and FIN races cannot be qualified by the host shim. `HTTP/1.0` and `HTTP/1.1` bounded legacy request lines are accepted by the seam; the proposed media carriage remains HTTP/1.1 only and denied in every case. Conditional OEM return and browser Digest fallback remain governed by the unchanged `FirstBootBridge.cpp`, not by these simulated routes.

## Existing bridge parity characterization

The active `firmware/src/boot/FirstBootBridge.cpp` is unchanged at this branch. It registers `GET /`, `/ui.js`, `GET` and `POST /api/v1/bridge/metrics`, status, filesystem plan, read-only OTA capabilities and factory-return status. `POST /api/v1/bridge/factory-return` remains inside `#if SHINO_ENABLE_FACTORY_RESTORE`; no media route is registered. `GET /` can issue a two-slot browser read cookie after `requireAuth()`; a valid cookie can read dashboard assets and metrics, while metric POST still calls `requireAuth()`. That call uses the existing `server.authenticate(...)` fallback followed by a Digest challenge on failure. This is source characterization, not a new authentication or browser execution result. The four metric values update only through `FslessMetrics::apply`; `FslessMetrics::stale()` remains strictly elapsed `>6000 ms`. The loop still calls `server.handleClient()` before redraw, `FactoryRollback::tick()`, watchdog feed and yield. A slow legacy body can therefore still delay those tasks. Host source execution confirms URI handoff to the parser; it does not run these actual route lambdas, JSON parsing, LCD or OEM upload callbacks.

**Protocol gate: HOLD** for any active media ingress until the structured-field version/parser, authority canonicalization, body framing, key/challenge lifecycle and independent security review are resolved. **Ownership gate: GO** only for the isolated deny-all compile/link and source-execution research described here.
