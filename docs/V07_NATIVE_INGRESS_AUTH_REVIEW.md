## 1. Threat model and the pre-body dependency

Assume an untrusted LAN/AP peer, a compromised or faulty PC sender, replay of captured requests, partial/slow connections, ambiguous framing, memory exhaustion, and simultaneous metrics/browser work. The private AP is network reachability control, not media authorization. Browser read cookies, the v2 `Authority` test object, `track_key`, transaction sequence, CRC32 and sender-supplied SHA-256 prove no identity. A compromised authenticated sender can still send resource-abusive but correctly signed data, so bounds remain necessary. No private credential or live device was accessed.

V2 currently puts **operation at byte 5 and transaction at bytes 16–31 of a 40-byte body header**. One generic `POST /api/v2/bridge/media` target cannot authorize an *operation-specific* write before reading those bytes. If one reads the 40 bytes first, that is a bounded pre-**payload** check, not pre-**body** authorization. If one authorizes only generic “media write,” the verifier has not yet authorized Begin versus Tile versus Commit, and an unbound or wrong-operation Commit becomes a confused-deputy risk. Merely adding an operation header is also insufficient unless the **actual** method/target, declaration and body digest are cryptographically covered, duplicates are rejected, and the binary header is checked for exact agreement.

The research outcome is a **two-gate architecture**, contingent on a new bounded single-owner ingress path. Stage 1 parses a capped request line and headers, obtains independently authenticated operation/transaction/epoch from the *actual target*, and rejects before reading any body byte. Stage 2 reads at most the fixed 40-byte v2 header, verifies exact duplication of operation/transaction/epoch and content length, then reads no more than 512 payload bytes under an absolute deadline. Only after checking a cryptographically protected `Content-Digest` against the complete 40+payload bytes may the record become eligible for the host receiver's state transition. That later body check is essential; pre-body identity authorization alone does not authenticate pixels or metadata.

### Architectural comparison

| Approach | What can be decided before body? | Finding / gate |
|---|---|---|
| Generic target; operation only in body | Method and broad media role only | **Reject** for operation-specific pre-body authority. Cannot prove a Commit was authorized as Commit. |
| Explicit operation and transaction in bounded request target, e.g. `POST /api/v2/bridge/media/{begin|tile|commit|abort}/{32 lowercase hex tx}` | Exact method, target, operation, transaction/epoch and principal, if covered by an independently verified standard request proof | **Preferred research candidate.** Keep target grammar exact, no query/decoding aliases; compare all duplicates with the binary header. This does not solve body integrity by itself. |
| Custom operation/transaction header | Possible if unique, bounded, canonically parsed and signed | Viable in principle, but adds critical-field parsing and duplicate/canonicalization work. A bare header is attacker-controlled. |
| Read fixed 40 bytes, then authorize | A bounded header can be checked before the 0..512 payload bytes | Useful **second gate** only. It cannot satisfy the required pre-body gate alone. |
| Normal `server.on()` handler or current `addHook()` alone | Handler runs after generic body parse; hook sees method/URL after unbounded request-line `String`, before headers | **Not sufficient.** Hook may stop or take a client, but a separate strict header/auth/framing parser and single-owner handoff would still be needed and proven. |
| Carefully reviewed bounded adapter on the existing port-80 owner | Potentially all stage-1 and stage-2 checks with fixed memory and finite work | **HOLD** until an isolated native source-executed implementation demonstrates no conflict with existing metrics, browser, OEM and watchdog paths. No second server or active route is proposed here. |

The synthetic model `tools/v07_ingress_research.py` uses the explicit target form solely to test this policy. It demands a test-injected `Decision` covering actual method, full target, Host, epoch, operation, transaction and RFC 9530-style `Content-Digest`; the model **does not parse or verify signatures**. `Signature-Input` and `Signature` fixture strings are inert placeholders, not credentials. Header limits (128-byte request line, 256-byte line, 1024 header bytes, 12 fields), a 64-byte read quantum and 2-second per-request absolute deadline are **research test parameters**, not approved ESP8266 heap/scheduling limits. Only the v2 40-byte fixed header, ≤512 payload and 8-second transaction deadline are existing wire-contract bounds. A candidate must justify all other limits against real library behavior and mixed load.

### Authentication source behavior

`ESP8266WebServer-impl.h:99-131` accepts **Basic** if the supplied base64 credential matches, even when the application challenges with Digest. Its Digest path (`:135-202`) extracts the client-supplied `uri` and hashes `current method : supplied uri`; it never compares that URI with `_currentUri`. It checks one server-wide `_snonce`, `_sopaque` and realm (`:154-160`); `requestAuthentication():215-229` replaces the shared nonce/opaque when challenged. The verifier uses `qop=auth` if found, accepts a no-qop legacy calculation, and has no observed nonce-count monotonicity/used-proof tracking or `auth-int` body hash. `_extractParam():91-95` searches substrings rather than uniquely parsing Digest parameters. Consequently `requireAuth()` is not a media-specific, exact-target, replay-safe, body-authenticated gate. Reusing OTA authentication authority or browser cookies is prohibited.

## 3. Standards-based production-auth design constraints

The strongest *research candidate* is a reviewed profile of [RFC 9421 HTTP Message Signatures](https://www.rfc-editor.org/rfc/rfc9421.html) over the actual `@method` and target/authority (or an equivalently exact set), `Content-Length`, `Content-Type`, and [RFC 9530 `Content-Digest`](https://www.rfc-editor.org/rfc/rfc9530.html), with required signature parameters for key/principal identity, nonce, creation/expiry or an independently justified challenge lifetime, and a media-specific tag. Exact operation and transaction/epoch appear in the signed request target and must match the binary v2 header byte-for-byte. The verifier must reject duplicate critical fields and any method/target canonicalization ambiguity. It can validate a signed digest declaration **before** body read; it must recompute that digest after the bounded body read and before Begin revocation/staging, tile mutation or Commit publication. A digest without the independently verified signature is just an attacker-supplied checksum. RFC 9421 is a toolkit, not a complete application policy; this document does not choose an algorithm, provision keys or implement it.

[RFC 7616 Digest `qop=auth-int`](https://www.rfc-editor.org/rfc/rfc7616.html) is another standards-based body-integrity path, but the pinned verifier implements only `qop=auth`/legacy MD5 and lacks exact-target/replay controls. `auth-int` cannot complete its body proof before reading the body; it would still require a separate pre-body authority gate and bounded streaming implementation. The installed Basic branch sends reusable credentials over a local non-TLS HTTP channel and cannot be silently inherited as media policy. Even a valid per-request proof needs a current boot/auth epoch, nonce replay lifetime, principal/session binding, media-only authority, bounded replay state, and fail-closed reboot behavior. Existing v2 high-water sequence is a **transaction consistency measure**, not a cryptographic nonce store or source identity.

Open questions requiring independent review before any native candidate: Where/how is a media-only key or verifier provisioned without changing the owner's installed system or leaking secrets? Which RFC 9421 algorithm/library fits ESP8266 code, stack and heap, and how are signature components canonicalized on this HTTP stack? How is a fresh unpredictable boot epoch/challenge issued and verified without a trusted wall clock, and how is nonce reuse bounded across reboot and concurrent requests? How are authorization revocation, duplicate Signature/Content-Digest, Host/path aliases, percent-encoding, query forms and abnormal connection reuse handled? What is the exact pre-header and per-poll API handoff from the active single owner, with measured effects on metric POST/GET, browser reads and the frozen OEM route? No answer is assumed from the host model.

## 4. Offline evidence and limits

`tools/test_v07_ingress_research.py` exercises **synthetic** finite streams, a strict candidate header policy and injected `Decision`. It covers invalid length syntax/overflow, duplicate/forbidden fields, TE/Expect/encoding, bounded lines/headers, no body read for denial, unrelated pending preservation, declaration mismatch, replay/stale epoch/wrong principal, partial/extra/changed bodies, absolute trickle timeout, and a separate four-metric freshness fixture. These tests prove only the model's state and read ordering. They do not execute `ESP8266WebServer`, the actual `FslessMetrics.cpp`, TCP, a signature library or the device. Its fake signature fields must never be mistaken for a valid RFC 9421 proof.

`tools/test_v07_pinned_core_probe.py` separately checks the three exact installed WebServer fingerprints and source ordering/auth/timeout markers. These are **source-backed static assertions**, not dynamic parser tests. `tools/v07_pinned_core_probe.py` also extracts the *unmodified* pinned `Stream::readStringUntil` and WebServer `readBytesWithTimeout` function bodies into a small C++ harness with fake stream/client dependencies. On this Windows host the Xtensa compiler passed **syntax-only cross-compilation**, which does not execute code. The actual host execution test was **SKIPPED** because no `g++`/`clang++` is on PATH. Even when executed on a compiler-capable runner, it covers only those two source primitives, not `_parseRequest()`, real `sendSize`, Wi-Fi, or application auth. Full parser execution and native ingress integration remain unverified.
