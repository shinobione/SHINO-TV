# SHINO // TV V0.8 Mission 1 — native resource budget worksheet

**Status: assumptions and future acceptance criteria, not target measurements.** No firmware was compiled with a media route, no ESP8266 heap/stack/CPU measurement was taken, and no device was contacted. The active V2.1 review-003 observations of 28,272 B minimum free heap, 26,216 B largest block and 12% fragmentation belong to another build without native media. They cannot be treated as the reserve for this proposal.

## Phase-specific storage and ownership

The following caps are proposed for research, subject to native source review. They count explicitly named payload/workspace bytes only. They do not count the pinned WebServer object, `WiFiClient`, lwIP/TCP, Wi-Fi, allocator headers, Arduino `String`, ArduinoJson, BearSSL, key table, SHA context, graphics, task stack, TLS, response buffer or fragmentation. A native implementation must measure or statically account for each exclusion.

| Phase | Candidate bounded storage and lifetime | Arithmetic floor or cap | Exclusions / release condition |
|---|---|---:|---|
| P0: one-owner accept and classify | 130-byte fixed request-line slot, partial line retained across polls | 130 B | Single client ownership and legacy handoff state; no second acceptor. Must cap before pinned `String::readStringUntil`. |
| P1: media header and Gate 1 | 1,024-byte total header slot including line; if P0 line is retained separately, count both | 1,154 B conservative overlap | Parsed field offsets, 32-byte digest, 64-byte signature, public key, challenge slots, signature-base/SHA work. Fixture base is 477 B; a native buffer/cap has not been chosen. Denial releases ownership without body workspace. |
| P2: verified 40-byte fixed record and ≤512 payload | P0 line + header slot + 40 + 512, if all coexist | **1,706 B** conservative envelope | Incremental digest, CRC, temporary parse state, TCP receive buffering and response. Header can be released after preserving required signed values, but no such optimization is credited. |
| P3: accepted Begin and staging | P2 envelope + one cover buffer + optional separate 512-byte canonical metadata copy | **6,826 B** at 48×48; **4,266 B** at 32×32; **2,218 B** coverless | JSON tree/canonicalization, renderer references and allocator overhead. The 512-byte metadata copy is an allowance, not a measured requirement. Accepted Begin revokes old art before one staging allocation. |
| P4: Tile and Commit | One 512-byte tile view, one 4,608/2,048-byte staging image; SHA reads the image in place | Image peak **4,608 / 2,048 / 0 B** | No second full image or Commit copy. SHA/BearSSL context, renderer and SPI transfer cost remain unknown. Ownership moves to renderer only after final SHA. |
| P5: cleanup and visible overlay | Pending buffer released on owned failure/expiry; committed buffer retained until next accepted Begin | One committed image at most | Cleanup must not alter four metric values, `received` or `lastReceivedMs`. Five-second return and freshness boundaries remain exact. |

V0.7's 48×48/32×32/text-only transport options are respectively 4,608/2,048/0 image bytes and 9/4/0 512-byte tiles. A 64×64 image is a comparison only: 8,192 image bytes and 16 tiles, rejected by v2. The selected revoke-first ownership model avoids a full-image Commit copy; any C++ `String`, JSON tree or graphics implementation that silently duplicates the image invalidates these floors. The conservative P2 arithmetic deliberately counts both the 130-byte classification slot and the 1,024-byte header slot even though the latter's wire byte cap includes the request line. A real implementation should report actual overlapping lifetimes, not subtract a theoretical sharing optimization in advance.

## CPU, stack and scheduling work budget

The V0.7 C++ handoff fixture limited input to **64 bytes per poll** and preempted an active slow client at **30 ms contention**. Its independent ingress candidate used a **2,000 ms request deadline**. These values are deterministic host fixtures, **not approved ESP8266 limits**. The only already specified transfer timer is the 8,000 ms absolute pending-transaction deadline, with exact-at-deadline acceptance. A native design must use wrap-safe elapsed arithmetic for every deadline and return control to the existing bridge loop during partial headers/body. The pinned WebServer's per-progress waits and current `handleClient()` location before redraw/OEM tick/watchdog feed make starvation a concrete risk.

Set a per-poll byte and CPU-time cap only after measuring: bounded line/header parse, structured-field parse, ECDSA-P256 verify, SHA-256 of 40–552 content bytes, metadata canonicalization, CRC32, final 4,608-byte image SHA, RGB565 SPI draw and response/close. Signature verification may be a single blocking call; its **maximum** elapsed time, stack high-water and watchdog interval matter more than a host mean. The host vector test executes Node/OpenSSL on a PC and supplies no ESP8266 cycle count. Source-executed pinned parser probes only show parser decisions with fake dependencies; they do not measure `WiFiClient` allocations or the active application loop.

The native acceptance worksheet should report, by phase and operation:

1. Exact source and dependency hashes, link-map flash/static RAM growth, compile flags and the complete call path that owns `_server.accept()`, `_currentClient` and legacy handoff. Prove one client owner and bounded read before any generic request-line `String` allocation.
2. Free heap **and largest contiguous free block** immediately before/after each P0–P5 transition, including header denial, signature success/failure, accepted Begin, staging allocation failure, Tile, Commit SHA, redraw and cleanup. Sample within phases, not only the existing one-second post-loop observer.
3. Worst stack/high-water for parser, RFC 8941 canonicalization, BearSSL ECDSA, SHA/CRC, JSON and graphics calls, including their overlap; account for recursion and interrupt/Wi-Fi use. Declare an engineering reserve for Wi-Fi/core variability **before** deriving a GO threshold. No universal safe-heap number is asserted here.
4. Maximum poll occupancy, accept-to-metrics POST completion and dashboard GET latency, largest interval between application watchdog feeds/yields, OEM tick delay and overlay return jitter under valid Tile bursts, slow/trickled headers, denied signatures, challenge-slot pressure, parallel legacy clients, partial FIN and repeated transfers. Report distributions **and worst observed values**, not only averages.
5. Failure injection at every allocation, parse, signature, digest, body, timeout and draw boundary. Denied/unrelated requests must leave pending transaction, artwork and four-metric state intact; verified owned failure must release staging once without extending the 8-second deadline. Challenge exhaustion and epoch failure must close admission without growing replay memory.
6. Long mixed-load replacement/coverless runs with phase-tagged fragmentation and contiguous-block minima, 48×48 and 32×32 separately. Verify the exact metric freshness comparison: at +6,000 ms fresh and at +6,001 ms stale; verify overlay return at exactly five seconds. A healthy HTTP path must not delay the application loop so those state semantics become unobservable.

Native compile-only work remains **HOLD** until the HTTP carriage/profile decisions and an independently reviewed bounded single-owner implementation plan are accepted under a separate instruction. An active route or device operation remains **BLOCKED** until the measurements, failure handling, authentication/key/challenge lifecycle and physical acceptance have their own review. This worksheet does not authorize a reserve estimate by subtracting host buffers from historical free heap.
