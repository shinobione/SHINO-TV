## 2. Native source: where ownership can change

`firmware/src/boot/FirstBootBridge.cpp:68` constructs the sole `ESP8266WebServer server(80)`; `:399-459` registers dashboard, metrics, status, read-only capabilities, filesystem plan and conditional factory-return routes, then calls `server.begin()`. `:469-480` calls `server.handleClient()` **before** redraw, `FactoryRollback::tick()`, heap sampling, `ESP.wdtFeed()` and `yield()`. The pinned `ESP8266WebServer-impl.h:280-291` owns `_server.accept()` and `_currentClient`. Its `:338-346` calls `_parseRequest()` before `_handleRequest()`. Pinned `Parsing-impl.h:47-82` accumulates an uncapped `String` request line **before** `addHook()`, and `:123-169` parses headers and requests the declared body size before an ordinary handler can call `requireAuth()`. The Mission 3 shim exercised these decisions, including a 5,000-byte line, 5,008-byte header, duplicate-field overwrite and an oversized `sendSize` request; it did not exercise actual target allocation.

| Alternative | Result |
|---|---|
| Register `server.on()` media or add only `addHook()` | **Reject.** Handler runs after generic body reception; hook runs after uncapped request-line allocation and before the strict header/signature decision. |
| Accept separately through `server.getServer()` or add another port-80 listener | **Reject.** `handleClient()` already accepts and owns clients; the public API has no proven adoption/replay contract. Two acceptors risk losing or double-handling a connection. |
| Replace the entire WebServer with a new shared HTTP implementation | Possible in principle, but a broad rewrite of metrics, browser session, OEM and response behavior. **HOLD** behind parity and resource evidence. |
| Minimal **single-owner pinned WebServer extension** before `_parseRequest()` | **Preferred future unconnected research seam.** One `_server.accept()` and one `_currentClient`; bounded incremental first-line read, then one of two mutually exclusive paths. Requires a reviewed core fork/patch and real source-executed tests. Nothing is patched in V0.7. |

The preferred handoff contract is precise:

1. At `HC_WAIT_READ`, before `String req = client.readStringUntil('\r')`, the **same** WebServer owner reads a bounded HTTP/1.1 request line incrementally into fixed storage. A partial line survives across loop calls. Malformed CRLF, overlong line, absolute-form target and timeout close that client without invoking the generic parser. Every connection, including ordinary routes, crosses this cap.
2. Classify the raw, undecoded target. The exact `/api/v2/bridge/media` namespace, including malformed or unsupported methods under that namespace, is reserved for the bounded media adapter and must never fall through to `onNotFound` or an ordinary POST handler. All other targets remain legacy traffic.
3. For legacy traffic, give the exact already-read bounded request line to a **minimally adapted** pinned `_parseRequest()` and leave every later byte on the same client untouched. Its existing route selection, Basic/Digest fallback, browser cookie logic and conditional OEM upload callbacks remain as they are. A wrapper that merely peeks/reads bytes outside WebServer cannot safely replay them to stock `WiFiClient`; this must be proved at source level. Legacy headers/body remain subject to existing generic-parser limits and risks, so this design does not claim a global HTTP DoS fix.
4. For media traffic, keep that client out of `_parseRequest()` and all legacy handlers. Parse at most 1,024 header bytes with a 128-byte line, 256-byte header-line and 12-field research cap. Reject duplicates and forbidden framing. An independently verified media principal and operation-specific authority must pass **before any body byte**. Check the 40-byte v2 header against the signed target, then receive no more than 512 payload bytes, verify signed `Content-Digest`, and only then offer a complete record to the host-wire state machine.
5. The owner has exactly one terminal action per client: response and close, or close on failure. Media never enters WebServer keep-alive, handler, upload or cookie state. `Content-Length` is exact; already-buffered trailing bytes cause rejection. A late pipelined request cannot be processed because the connection closes. Waiting for peer FIN *before* replying could deadlock a well-formed client, so a native close/pipeline policy needs explicit TCP tests before claiming literal rejection of every byte sent later.
6. An unclassified or unauthorized failure closes only that request and cannot revoke unrelated artwork or change a pending transaction. Once a verified principal/transaction owns pending work, partial reception, digest failure, disconnect or absolute expiry invokes the receiver's terminal cleanup exactly once. The 8-second transaction deadline is independent of request progress. Buffer ownership moves from ingress to receiver only after complete proof; one image staging buffer moves to display ownership after final SHA-256, without a full-image copy.

The host handoff lab tests a provisional **64-byte maximum input per poll**, 130-byte first-line storage and a **30 ms contention preemption** of an active slow client. These numbers are research fixtures, not approved native deadlines. A preempted verified owned transfer terminates; an unclassified one has no media side effect. The current candidate uses `now < start` checks and is not a proven wrap-safe ESP8266 `millis()` design. The actual core's `HTTP_MAX_DATA_AVAILABLE_WAIT` of 30 ms applies while no current bytes are available; it does not cure a trickle read already inside blocking `_parseRequest()`. A native prototype must prove fair loop return and exact client lifetime with real socket cases.

## 3. Concrete media-only authentication profile for review

The proposed protocol profile uses [RFC 9421 HTTP Message Signatures](https://www.rfc-editor.org/rfc/rfc9421.html), [RFC 9530 `Content-Digest`](https://www.rfc-editor.org/rfc/rfc9530.html), [RFC 8941 Structured Fields](https://www.rfc-editor.org/rfc/rfc8941.html), and strict HTTP/1.1 origin-form request targets. **Candidate algorithm:** RFC 9421 `ecdsa-p256-sha256`, with the 64-byte raw `r || s` signature. A media-only PC principal retains the private key; the device would hold only an approved public-key allowlist. Pinned `tools/sdk/include/bearssl/bearssl_ec.h` exposes P-256 and `br_ecdsa_i31_vrfy_raw`; `bearssl_hash.h` exposes SHA-256. No RFC 9421/RFC 8941 canonicalization implementation has been selected or measured. This is a design candidate, **not** production authentication PASS. HMAC-SHA256 is also standardized by RFC 9421, but would put a shared signing secret on the device; that provisioning and extraction risk makes it a less defensible first candidate here.

Require exactly one `Signature-Input`/`Signature` pair with one label, one `Content-Digest` dictionary member (`sha-256` with exactly 32 decoded bytes), one `Host` matching a configured device authority, one `Content-Type`, one `Content-Length`, and `Connection: close`; reject all duplicate critical fields, `Transfer-Encoding`, `Expect`, content encoding, trailers, multipart, query, percent-encoding, non-origin targets, alternate casing/aliases outside the reviewed profile and ambiguous whitespace. The required RFC 9421 covered components, in fixed order, are **`@method`, `@request-target`, `@authority`, `content-type`, `content-length`, `content-digest`**. `@request-target` binds the raw HTTP/1.1 origin-form path including operation and 32-hex transaction; `@authority` binds the one Host value. RFC 9421 warns that `@request-target` is hard to reconstruct across HTTP versions, so the profile must fail closed on any version other than HTTP/1.1 and be redesigned if that changes. The derived components must be supplied from the bytes actually parsed at ingress, not a client-declared Digest `uri` or decoded route alias.

The reviewed `Signature-Input` would require fixed `alg="ecdsa-p256-sha256"`, a `keyid` mapped to a media-only principal and allowed operations, a single-use server challenge in `nonce`, and a media-specific `tag`. These parameters enter RFC 9421's signature base through `@signature-params`. A 16-byte challenge encoded as 22 base64url characters and short bounded key/tag IDs yield an illustrative 213-byte Signature-Input line; a complete seven-field sample header is about 587 bytes, inside the research 256/1,024-byte caps. These are sizing examples, **not** parser acceptance evidence. An RFC 8941 Structured Fields parser, base64 decoder, component canonicalizer, exact signature-base builder and RFC test vectors are required; matching raw strings in a mock verifier is insufficient.

**Gate 1, before body:** map `keyid` to a provisioned media public key/principal, verify the ECDSA signature over the actual components and the signed digest *declaration*, validate boot epoch in the target and a current unused challenge, and atomically consume that challenge. Denial reads no body and cannot mutate unrelated pending or metrics. **Gate 2, after bounded body:** incrementally compute SHA-256 of the exact 40+payload bytes and compare with the signed RFC 9530 digest before metadata parse, old-art revocation, staging, tile write or Commit. Then the host-wire receiver separately checks envelope CRC32 and final whole-image SHA-256. CRC32, final image hash, transaction high-water and `track_key` do not authenticate the sender.

No trusted wall clock is assumed. The device would need a fresh unpredictable boot/auth epoch and challenge issuance bound to that epoch, with an absolute monotonic lifetime. RFC 9421 `created`/`expires` cannot be accepted as a clock-based replay gate unless a trusted time source is established; a profile can omit them and require the server-issued single-use `nonce` instead. Keep a fixed number of outstanding challenges per media key, consume on successful pre-body proof, reject unknown/used/expired values, never evict a live challenge to admit another, and fail closed at capacity or counter exhaustion. A reboot discards all outstanding challenges and starts a new unpredictable epoch; sequence high-water resets only with that new authority. Concurrent clients need atomic consume under the single owner; captured Tile/Commit signatures must not replay even though the v2 transaction ID is unchanged across records. The slot count, entropy source/health test, challenge transport, issuance rate limit and round-trip cost for nine tiles remain **unresolved**. A 64-bit wire epoch does not itself prove replay safety.

Public-key provisioning and revocation require a separately approved, auditable owner process. No private key belongs in source, CI, logs, browser cookies, rescue credentials, OEM return logic or an installation artifact. Device public-key storage/rotation, PC private-key protection, key compromise response and media-only role mapping are undecided. Signature validation provides no content confidentiality. The exact BearSSL code/link path, RFC canonicalization implementation, signature verification time, SHA context, flash growth, stack high-water, heap/largest-block use and watchdog interval require native measurements. Until independently reviewed and measured, the verifier is **BLOCKED**.

## 4. Wire, memory, scheduling and parity constraints

The separate wire-v2 record remains `STV7`, version 2, 40-byte big-endian fixed header, 0–512 payload and 552-byte maximum request body. Its image modes remain 48×48 RGB565LE (**4,608 B**, nine tiles), 32×32 (**2,048 B**, four tiles) and text only (**0 B**); 64×64 is comparison only and rejected by v2. Old artwork is revoked only after a fully verified, valid accepted Begin; at most one pending transaction exists, and Commit is bound to that principal/epoch/transaction. Whole-image SHA-256 is checked in place before one staging buffer changes display owner. The 8,000 ms deadline is absolute; one 64-bit sequence high-water plus bounded challenge slots is the proposed replay memory. Five-second overlay expires at `now >= overlay_until`, while numeric metric freshness remains unsigned elapsed **strictly >6000 ms**. An unrelated unauthorized request must never clear another transaction or any of the four metric values, `received`, or `lastReceivedMs`.

**HTTP-carriage discrepancy to resolve before a native prototype:** Mission 1 described a prospective generic `POST /api/v2/bridge/media`; Missions 2–3 use `/api/v2/bridge/media/{operation}/{tx}` so Gate 1 can authorize Begin versus Tile versus Commit before reading the body. The explicit target is the defensible research choice. It requires a formally reviewed HTTP carriage amendment, sender/receiver parity and exact binary-header agreement. No frozen V0.5 codec change or v2 binary compatibility claim follows from this choice.

The fixed candidate buffers total **1,706 bytes** (1,024 header + 40 fixed + 512 payload + 130 preclassification line) before state, verifier, client/TCP, parsed metadata, SHA, stack or image. Adding one 512-byte metadata copy and the 48×48/32×32 image yields illustrative simultaneous storage sums of **6,826 / 4,266 bytes**, or **2,218 bytes** coverless; these are arithmetic planning floors, not native allocation requirements or measured peaks. Mission 3 measured `sizeof(Gate)=1,872` and `sizeof(Pending)=56` only on MSVC x64. The owner's older free-heap/largest-block observations come from a different build without media. No safe reserve or native phase budget has been established.

The active loop calls HTTP handling before redraw, OEM tick and watchdog feed. Future measurements must include maximum per-poll CPU time and bytes, accept-to-metrics-update latency with slow competing clients, inter-feed watchdog interval, largest contiguous free block, stack high-water, renderer/SPI time, digest and ECDSA CPU, challenge pressure, and 5-second overlay return jitter. A source-executed host count of 64 bytes per poll or a synthetic metric interval proves neither fairness nor watchdog safety. The normal legacy body parser also remains unbounded for attacker declarations; any global ingress security claim requires a separate decision to harden those existing routes.
