# SHINO // TV V0.8 Mission 1 — proposed HTTP carriage contract

**Status: host-only amendment proposal.** This ratifies, for research review, the explicit target that V0.7 Missions 2–4 used to solve pre-body operation authorization. It does not alter the frozen V0.5 codec, the V0.7 40-byte media-wire-v2 binary record, or any native HTTP route. V0.7 Mission 1's illustrative generic `POST /api/v2/bridge/media` is superseded **only in this proposed v2 HTTP carriage**. The proposal requires independent sender/receiver agreement before a native prototype.

## Exact request target and identity

The only proposed media request line is `POST /api/v2/bridge/media/{operation}/{tx} HTTP/1.1\r\n`. `operation` is one lowercase ASCII token: `begin`, `tile`, `commit` or `abort`. `tx` is exactly 32 lowercase hexadecimal ASCII characters. The decoded 16 bytes are eight big-endian epoch bytes followed by eight big-endian sequence bytes; both integers must be nonzero. The first eight transaction bytes must equal the nonzero `epoch` at binary offsets 8–15. The last eight are the strictly increasing transaction sequence at binary offsets 24–31. A transaction keeps the same target `tx` on every record, while **every HTTP request needs a different single-use challenge**.

The method, spacing, HTTP version, path segments and hexadecimal case are literal. Reject queries, fragments, percent escapes, dot segments, doubled slashes, trailing slash, absolute-form or authority-form targets, Unicode lookalikes, path decoding/normalization, extra whitespace and unsupported methods. Reserve the entire raw `/api/v2/bridge/media` namespace, including malformed candidates, for denial by the bounded owner; it must never fall into legacy route handling. A raw target outside that namespace follows the separate legacy handoff contract. `@request-target` is the actual origin-form request-target bytes from this HTTP/1.1 line, not an application-decoded path or client-supplied Digest URI. A change of HTTP version or proxy/intermediary behavior needs a new profile review.

## Bounded header profile and two gates

Proposed research caps, **not native-qualified values**: 130 bytes including request-line CRLF, 256 bytes per header line including CRLF, 1,024 bytes total request line plus headers through CRLFCRLF, and 12 header fields. The seven required unique fields are `Host`, `Content-Type`, `Content-Length`, `Content-Digest`, `Connection`, `Signature-Input` and `Signature`; field names compare case-insensitively for duplicate rejection. The host lab accepts no other field, no continuation/obs-fold, bare LF, tabs, controls, leading/trailing value whitespace or malformed CRLF. In particular reject `Transfer-Encoding`, `Expect`, `Content-Encoding`, `Trailer`, multipart, duplicate `Host`/length/signature/digest, and TE+CL ambiguity. Native acceptance of standard optional fields versus this strict allowlist remains a review decision.

`Host` must be the one configured device authority, represented in the signed `@authority` component; the fixture `tv.test` is not a production host. `Content-Type` is exactly `application/vnd.shino-tv.media-wire-v2`; `Connection` is exactly `close`. `Content-Length` is canonical base-10 without sign, leading zero, suffix or whitespace and is in 40–552. It counts **only** the 40-byte binary header plus `payload_len`, with no trailer. `Content-Digest` and signature fields follow the narrow profile in [V08_CRYPTO_PROFILE_REVIEW.md](V08_CRYPTO_PROFILE_REVIEW.md).

**Gate 1:** after only the bounded request line and headers, use a provisioned media-only public key to verify the RFC 9421 signature over the *actual* method, target, authority, content type, length and digest declaration. Check key/principal role, operation, target epoch, current boot epoch, current unused challenge and deadline, then consume the challenge atomically. An unauthorized or malformed request closes without reading any body byte or changing pending media/artwork/metrics. A signed digest declaration is only a commitment to later bytes, not proof that those bytes arrived.

**Gate 2:** after Gate 1, read exactly 40 bytes followed by at most 512 payload bytes under an absolute request deadline. Verify SHA-256 over the exact complete body against the signed RFC 9530 `Content-Digest` **before** any media state transition. Then verify exact binary-header agreement, payload shape and CRC32. Missing bytes, early FIN, a changed body, or already-received trailing bytes fail; the owner closes the connection. A real TCP policy for bytes arriving later and for pipelining remains unproved. Avoid waiting for FIN before replying to a well-formed client. No legacy handler, cookie, Basic/Digest fallback or upload callback may see a media request.

| Signed target operation | Binary byte 5 | Binary payload requirement | Tile index at bytes 32–33 |
|---|---:|---:|---:|
| `begin` | 1 | 1–512 canonical metadata bytes | 0 |
| `tile` | 2 | exactly 512 image bytes | valid next index, 0–8 for 48×48 or 0–3 for 32×32 |
| `commit` | 3 | 0 | 0 |
| `abort` | 4 | 0 | 0 |

The fixed record is unchanged: `STV7` at 0–3; version 2 at 4; zero flags at 6–7; big-endian epoch at 8–15; 16 transaction bytes at 16–31; big-endian tile index and payload length at 32–35; payload CRC32 at 36–39. The binary transaction must equal all 16 decoded target bytes, not merely its sequence. `Content-Length = 40 + payload_len`. Begin metadata's canonical `tx` must equal that same target. For a Tile, the pending variant must make the index and expected size valid. The host lab checks fixed header, identity, operation shape and CRC; the existing V0.7 host receiver remains the source of metadata, pending-state, image SHA-256 and display semantics. None of these later checks substitutes for Gate 1.

One pending transaction and the absolute 8,000 ms Begin deadline remain unchanged. A competing Begin cannot replace it or reset time. A denied, unrelated request cannot revoke an old cover or terminate another pending transaction. Only a verified and fully valid accepted Begin crosses the revoke-old boundary; verified owned partial/failure cleanup follows the V0.7 receiver contract. Final image SHA-256 checks staging in place before ownership transfer. The four metrics, `received` and `lastReceivedMs` are separate. Their freshness remains strictly `>6000 ms`, and the overlay return remains `now >= overlay_until` at five seconds.

## Host evidence and unresolved native handoff

`tools/v08_crypto_lab.js` is an isolated byte-stream model. Its tests show 0 body reads and 0 body allocation for Gate 1 denial, real P-256 signature verification, bounded body allocation after Gate 1, and signed-target/binary disagreement rejection. Its `ByteStream` already holds a test buffer; the read counter proves call ordering **within the model**, not that a native TCP/WebServer layer avoids read-ahead or allocation. The pinned WebServer parses an unbounded request line and ordinary POST body before handlers; `server.on()` or `addHook()` alone still cannot implement this contract. V0.7's minimal **single-owner preparse extension** remains only the preferred unconnected research seam. Legacy first-line replay, connection ownership, deadline wrap, partial reads and coexistence with numeric/browser/OEM handlers need source-executed native evidence under a separate instruction.
