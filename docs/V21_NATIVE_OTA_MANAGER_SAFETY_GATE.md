## Why we cannot just expose POST /update

The 4-MiB chip has a `4m3m` SHINO layout and application OTA staging end `0x100000`. Streaming `Update.write()` modifies staging flash **before** the final whole-file digest can be established. `Update.end(false)` is a late verification/commit boundary, not an atomic full-flash rollback. A broken or incompatible application can still remove Wi-Fi recovery. The separately installed OEM-return module is only an exact manufacturer **application** writer, not an owner full-flash backup; it does not rescue a nonbooting SHINO.

Our previous real owner round-trip SHINO→OEM→SHINO succeeded, but that does **not** establish indefinite OTA/power-failure safety.

## Phase B research increment: signed package verifier (OFFLINE ONLY)

`tools/verify_signed_ota_package.py` now parses the exact core-3.1.2 transport `UNSIGNED_ESP8266_BIN || RSA2048_SIGNATURE_256_BYTES || uint32_le_signature_size`. It requires separately reviewed SHA-256 values for both the public signing PEM and the **unsigned** application, checks DIO/4-MiB/40-MHz headers and FS-less markers, validates the `4m3m` linker and signed **total transfer** staging geometry, then independently calls OpenSSL RSA/SHA-256 verification using only the public key. It never reads a signing private key or connects to the device and **always returns `permission_to_flash=false`**. It is a research verifier, not a package signer, on-device verifier, credential provisioner or updater.

Important detail verified in upstream `Updater.cpp`: `Update.begin(size, U_FLASH)` receives the **entire signed transfer size** for OTA staging. At `Update.end(false)`, the native verifier validates the appended signature and subtracts the trailer before scheduling eboot to copy only the unsigned application. The size gate must therefore use signed transport bytes, not just raw firmware bytes. `Update.installSignature()` sets state on the shared global Updater; OEM-return route still needs a completely separated and reviewed pinned-image-only policy. No writer has been added.

Tests generate ephemeral RSA-2048 fixture keys outside the repo, verify a valid signed sample, then reject unsigned input, corrupt signature/payload, invalid trailer, appended bytes, wrong public key/trust-anchor hash, wrong independent image hash, layout mismatch, insufficient stage budget and symlinks. Fixture private keys are deleted on completion; these are NOT production signing keys.

## Critical verified upstream behavior: signature mode overrides OEM MD5 validation

Review of pinned ESP8266 Arduino Core `3.1.2` (`cores/esp8266/Updater.h`, `Updater.cpp`, `Updater_Signing.h`) identified a **dangerous shared-state interaction**: `Update.installSignature(...)` sets persistent pointers in the process-global `Update` object; its `_reset()` does not clear those pointers. During `Update.end(false)`, the core follows `if (_verify) { signature verification ... } else if (_target_md5.length()) { MD5 verification ... }`. Consequently the existing OEM return's `Update.setMD5(SHINO_FACTORY_MD5)` is **not an enforced OEM image pin when signature verification is active**. Its MD5 check is skipped. Merely preserving the OEM-return route alongside global signed OTA or temporarily switching the verifier off would therefore be unsafe and is **NOT approved**.

We have added independent compile-time blockers:
- Generated owner/CI policy now explicitly defines `SHINO_ENABLE_NATIVE_SIGNED_OTA 0`. The first-boot bridge statically refuses a nonzero value. There is still **no signed-OTA writer**.
- OEM-return source includes the actual core `Updater_Signing.h` and fails compilation if either `SHINO_ENABLE_NATIVE_SIGNED_OTA != 0` or both `SHINO_ENABLE_FACTORY_RESTORE` and core `ARDUINO_SIGNING` are enabled.
- Source regressions forbid generic updater endpoints or unreviewed runtime `Update.installSignature(nullptr, nullptr)` workarounds.

Before permitting both native signed OTA and manufacturer return in one build, replace the legacy *unsigned* OEM path with a separately reviewed **signed pinned-OEM package path** that verifies both the official raw manufacturer image (494,144 B and independently pinned SHA-256) and an owner-trusted signature. It must use the core verifier's real semantics, count **full signed transport bytes** for OTA space and never introduce an unconditional unsigned bypass. Review the effect of key loss separately. Alternatively maintain *mutually exclusive build profiles* but explicitly disclose that a signed-only profile does not preserve the currently proven unsigned OEM return. Neither alternative is implemented or authorized now.

**Core source audited:** [3.1.2 Updater.h](https://github.com/esp8266/Arduino/blob/3.1.2/cores/esp8266/Updater.h), [3.1.2 Updater.cpp](https://github.com/esp8266/Arduino/blob/3.1.2/cores/esp8266/Updater.cpp), [default Updater_Signing.h](https://github.com/esp8266/Arduino/blob/3.1.2/cores/esp8266/Updater_Signing.h). This is code-path reasoning, not proof of real-device rescue or power-failure safety.

## Signed **and exact** OEM return package — offline proof (NOT a device writer)

The new `tools/verify_signed_oem_return.py` enforces two **independent** conditions for any proposed future manufacturer-return transport: (a) the unsigned payload is **byte-for-byte** the OEM V9.0.44 application extracted from the officially pinned ZIP; (b) the 256-byte RSA-2048/SHA-256 signature over that exact raw payload verifies with an owner-controlled public key whose PEM SHA-256 is independently supplied, not self-declared by the uploaded package. It also hard-pins manufacturer application SHA-256 `a6421f5bfee7860d97bed26620c346b8008f503e513702d4bfdf6e01010a7718` and manufacturer ZIP SHA-256 `cfbef50754ec552f9791878931c5f3643734de15f3c81cebdecf7ce05b28230f` in the verifier itself, so feeding a substitute self-consistent manifest cannot authorize an alternative manufacturer image. No private signing key is used or generated by this verifier.

For the existing **494,144-byte application**, a core-format RSA-2048 signed transport has **494,404 bytes**: original payload + 256-byte signature + 4-byte little-endian signature length. The geometry check sizes the **entire 494,404-byte transport** against the `4m3m` OTA staging ceiling, actual-model current sketch gap, 4-KiB guard and manually supplied runtime `getFreeSketchSpace()`, rather than incorrectly treating the signature trailer as free. It validates DIO/4-MiB/40-MHz OEM header, original archive manifest and actual independent OpenSSL signature check. A passing result always returns `permission_to_flash=false`, `on_device_signed_oem_writer_compiled=false` and explicitly acknowledges **application-only**, not original filesystem or full-flash recovery.

The test suite builds a **synthetic** 494,144-byte fake OEM reference, temporary RSA-2048 signing keys, private fixture archive and manifest; it accepts one correctly signed byte-exact fixture and rejects signed altered OEM payloads, bare unsigned OEM, corrupt signature or length trailer, extra/truncated bytes, wrong owner key or public-key pin, alternate original archive/manifest, wrong flash layout/capacity and insufficient staging. Tests patch manufacturer hash constants **only inside test fixture scope**; there is no CLI override of the production pins. Neither the real manufacturer's binary, owner signing private key nor any installable signed package is checked in or published.

**Critical on-device design gate, NOT YET IMPLEMENTED:** the future actual signed OEM route must authenticate the specific privileged POST and explicit owner action, hash the first *exactly 494,144 raw image bytes* incrementally during bounded streaming and compare them to the compiled official SHA-256 **before calling the core's `Update.end(false)`**, while configuring the owner's one trusted signature verifier for BOTH native SHINO and OEM packages. `Update.end(false)` then verifies the RSA signature **before** it schedules eboot copy, and the core copies only the unsigned application. If raw hash or upload fails, **never call a potentially committing successful `Update.end(false)`**: block retries and restart to clear staged transient updater state, after separately reviewing core semantics. Ensure actual hardware flash mode matches the signed DIO header, since core Updater may rewrite the header's flash-mode byte in staging and invalidate an uploaded signature when they differ. Never use `Update.end(true)`, an unsigned OEM fallback, or a temporary `installSignature(nullptr, nullptr)` exception. A signed owner key does not itself prove a compatible manufacturer image. This is still an application-only fallback from a *running* SHINO; a nonbooting device cannot serve its Web recovery.

## On-device-compatible SHA-256 OEM raw precommit (COMPILE-ONLY; NOT WIRED)

`firmware/include/recovery/SignedOemPrecommitGate.h` contains the bounded **production-pin** C++ state machine; `firmware/src/recovery/SignedOemPrecommitProbe.cpp` explicitly instantiates all its methods against the ESP8266 core's native BearSSL `br_sha256_init/update/out` adapter during firmware compilation. **No callable OTA handler or API route uses it.** The installed `review-002` does not include this code.

The state machine expects exactly 494,404 transport bytes (494,144 raw OEM bytes, 256 signature bytes and 4 little-endian trailer-length bytes), checks the exact pinned V9.0.44 image's four header bytes even if split across tiny chunks, hashes ONLY the first 494,144 raw bytes progressively (at most 4,096 bytes accepted in one input call), keeps only the last 4 trailer bytes, checks declared final total, validates RSA-2048 trailer length and compares the complete 32-byte SHA-256 result against the immutable compiled OEM digest without early byte-exit. It is non-copyable and one-shot; malformed header, null/empty/oversized chunks, corrupted payload, overrun, early EOF, bad trailer, duplicate finish and abort fail closed. A success is named `ExactRawAwaitingCoreSignature`, deliberately **not** approval to install: it has **NOT** verified the RSA signature nor boot compatibility.

`tools/test_signed_oem_precommit.py` compiles and executes this exact templated C++ gate against OpenSSL's EVP SHA-256 as host-only adapter, including header and trailer split across chunks, altered payload, mutated RSA trailer (which MUST still pass the raw hash guard, demonstrating the necessary independent core RSA check), length errors, repeated finish and explicit abort. The separate target compiler type-checks every method against real BearSSL, but **no actual on-device execution, OTA write or power-cut test** is implied. The single-device offline CI also compiles the C++ production-pin host harness and runs it against the independently pinned original manufacturer bytes obtained transiently from the verified ZIP; a one-byte change must fail. All tools and CI still report `permission_to_flash=false`.

**Remaining integration, blocked:** on any separately reviewed future signed OEM route, the authenticated upload adapter must compute this raw hash while bounded data is streamed to staging and refuse to call the core's potentially committing `Update.end(false)` unless the raw gate returns `ExactRawAwaitingCoreSignature`. The **same pinned owner RSA verifier** must then independently verify the entire signed package inside the core's `Update.end(false)` before eboot is scheduled. Errors after complete staging MUST NOT invoke `Update.end(false)` just to reset; resolve Updater abort/reboot and pending eboot semantics in separate tests. A stage write can occur *before* hashes are known; this design does not assert atomic rollback or guarantee recovery after power loss. The old unsigned OEM-return path must remain compile-incompatible with global signing until a separate signed+exact replacement route is implemented and reviewed.

## Last-mile commit sequence — HOST EMULATION ONLY (NO ON-DEVICE WRITER)

`firmware/include/recovery/SignedOemCommitBarrier.h` now defines a separate, non-copyable, dependency-injected **host-only** ordering contract for a future signed OEM application transfer. It is not included in `FirstBootBridge.cpp` or `FactoryRollback.cpp`, has no HTTP route, embedded signing key, production Updater adapter or device operation. The booleans `privilegedOwnerIntentValidated` and `coreSignedVerifierConfigured` are **assumptions supplied by test fixtures**, not authentication, owner consent or a trusted production signer. A real independently audited HTTP adapter is still needed.

The proposed order is: separately validated privileged manual intent and trusted signer configuration → exact signed transport length → staging adapter start → bounded raw-OEM hash/transport accounting for every chunk → staging adapter write → final exact raw SHA-256 + 256-byte signature-length trailer + exact bytes → staging completion/no errors → **one** `adapter.end(false)`. The real ESP8266 Arduino Core 3.1.2 checks the RSA signature **inside** `UpdaterClass::end(false)`, before its `eboot_command_write`; a bad RSA signature therefore legitimately reaches the end call but **must return false and never schedule eboot**. There can be no honest blanket assertion that "no signature failure reaches end": core end is the RSA verification boundary itself. A raw hash mismatch, truncated/oversized transfer, invalid header/trailer, unauthenticated request, missing verifier flag, staging fault or manual abort must NOT call end. Duplicate completion/rearm and `end(true)` are forbidden. The pure barrier never requests reboot, retries or clears the real Updater's pending state.

`tools/signed_oem_commit_barrier_probe.cpp` emulates the relevant core end contract using a host-only staging vector and **actual OpenSSL RSA-2048/SHA-256 signature verification with a disposable generated test key**. Only after the host verifier returns success does its fake `eboot_scheduled` become true. The tests check a true signed unchanged synthetic OEM, a correctly signed **modified** OEM (raw guard rejects *before* core end), a corrupted/other-key signature (raw guard succeeds; core end called once; no eboot), unsigned/truncated/overlong input, bad header or trailer, absent owner intent/signer, wrong declared/final total, failed/short stage write, abort, >4-KiB chunk, repeated finish and rearm. This is an **integration model**, not execution of real core flash/eboot, real Digest/CSRF validation, a USB recovery path, or evidence of power-cut safety. It uses no actual signed firmware and cannot produce an owner install packet.

The final embedded writer may only be considered after separate source review of the real ESP8266 core signature state and public-key provisioning, a strict private-AP request handler with explicit owner action, flash geometry and per-chunk timeout handling, verified staged upload-abort/reboot semantics, end(false) behavior on real hardware under supervision, and full release provenance. Until then this PR remains DRAFT and `physical_installation_authorized=false`.

## HTTP boundary and manual consent — raw streaming research gates (NOT LIVE)

Review of the **pinned** ESP8266 Arduino Core 3.1.2 reveals two concrete limitations in the currently used `ESP8266WebServer` implementation that are unacceptable as an OTA security boundary:

1. Its `Parsing-impl.h::_parseRequest` copies an ordinary non-multipart POST body into `String plainBuf` using `readBytesWithTimeout(client, contentLength, plainBuf, ...)`. Our proposed ~494,404-byte signed OEM upload must **not** enter that buffered path or a multipart handler designed without a reviewed strict header pre-parser. The eventual transport requires a dedicated bounded streaming socket/parser which exposes and validates the *raw* request metadata **before any body/staging write**.
2. The parser assigns `_hostHeader = headerValue` and `contentLength = headerValue.toInt()` as repeated headers arrive. Merely reading `server.hostHeader()`, `server.header(...)`, or `server.authenticate(...)` after the fact cannot prove the raw wire request contained exactly one unambiguous Host and Content-Length. Its `ESP8266WebServer-impl.h::authenticateDigest` uses the `uri` supplied inside the Digest response to calculate H2, but does not explicitly bind that string to the actual current URI; it incorporates client `nc` into the hash without maintaining replay-counter state. **Do not use the dashboard's existing Digest checker as the privileged OTA verifier.** This is a source-audit observation about this pinned core; the current dashboard is left alone.

We added **pure, disconnected** `firmware/include/boot/NativeOtaRawHeaderGate.h`: a maximum 2,048-byte no-heap CRLF-only HTTP/1.1 request-header pre-parser, exact POST URL for `/api/v1/bridge/ota/arm` or `/api/v1/bridge/ota/upload`, exact canonical `Host: 192.168.4.1` and `Origin: http://192.168.4.1`, exact MIME/body bounds, explicit Content-Length, Digest *syntax presence only*, lowercase 128-bit intent token for upload and fail-closed rejection of **all duplicated header names** (case insensitive), Transfer-Encoding, Expect, gzip Content-Encoding, folded headers, CR/LF injection, oversized/overlong framing, query strings, missing Origin and wrong method. Cookie is merely observed and confers ZERO privileges. It does NOT parse firmware body, authenticate Digest or accept a release. The future connection handler must retain the original header bytes, pass only the header slice, enforce full fixed-length body read with timeouts, close the socket without pipelining and separately verify the actual private-AP listening interface/peer. A passing HTTP syntax precheck alone has NO ability to start an update.

`firmware/include/boot/NativeOtaManualConsentGate.h` adds a pure 60-second, **one-shot** manual-intent binding for peer IP, exact signed package kind (native SHINO or exact OEM), signed byte count, caller-supplied nonzero 128-bit token and 32-byte SHA-256 *of the selected signed transport*. A failed guess, changed peer/size/hash/kind, expired token, absent simulated Digest/Origin approval, abort or replay irreversibly closes that gate instance. Success is deliberately named `ConsumedForReviewOnly`. Its external booleans are **not actual proof**, and a SHA-256 offered by an untrusted upload is only file/consent binding, **not publisher authenticity**. The future device must use hardware CSPRNG, dedicated audited Digest verifier (including URI/method, qop, nonce, nonce-count and replay protection), separately stored owner public signing key, explicit UI confirmation after review of model/version/digest, and real upstream RSA verification before any final commit. None of that is connected to HTTP here.

Two host-compiled C++ adversarial probes execute these exact policies: duplicate/mixed-case framing, malformed header/control bytes, cookie-only, cross-origin, incorrect MIME and length, wrong token, replay, 60s expiry including `millis()` rollover, altered peer/kind/digest and proof-booleans. `FirstBootBridge` registers **NO** arm/upload/install route and does not include either module. No byte from the owner device is read and no firmware, FS, credential or key is published.

Pinned source references: [ESP8266WebServer 3.1.2 request parser](https://github.com/esp8266/Arduino/blob/3.1.2/libraries/ESP8266WebServer/src/Parsing-impl.h), [3.1.2 Digest implementation](https://github.com/esp8266/Arduino/blob/3.1.2/libraries/ESP8266WebServer/src/ESP8266WebServer-impl.h). These issues bar enabling a traditional `server.on("/update", HTTP_POST, ...)` writer just because a compile or host fixture passes.

## Dedicated strict SHA-256 Digest proof (HOST TEST ONLY)

`firmware/include/boot/NativeOtaStrictDigestGate.h` is a pure, non-copyable, 60-second **single-use** HTTP Digest SHA-256 (`qop=auth`) claim verifier with a dedicated `SHINO-OTA` realm. It is **not registered** in `FirstBootBridge`, contains no owner credential, does not generate challenges and cannot authenticate a real request without a future raw TCP server adapter. It deliberately does NOT invoke the generic `ESP8266WebServer::authenticateDigest()` mechanism audited above.

The future standalone challenge must be generated from fresh independent hardware CSPRNG and include dedicated nonce and opaque values plus `algorithm=SHA-256, qop="auth"`. The verifier receives the *actual* normalized method/URI exclusively from the already validated raw-request parser, never from an untrusted Digest field; the only accepted method is POST, and the only accepted route is the challenge-bound exact `/api/v1/bridge/ota/arm` or `/api/v1/bridge/ota/upload`. It rejects missing/duplicate/unknown/escaped Digest fields, wrong username/realm/nonce/opaque/algorithm/qop, a mismatched URI, malformed response, incorrect peer or invalid proof. It requires exactly `nc=00000001`, a bounded independent `cnonce`, an externally provisioned `HA1 = SHA256(username:SHINO-OTA:password)` derived from private owner credentials, and computes `SHA256(HA1:nonce:nc:cnonce:auth:SHA256(POST:actualURI))` with an injected SHA-256 implementation. A failed attempt consumes the challenge; success is named **`VerifiedForReviewOnly`**, not owner installation permission. It does not accept a GET cookie in place of proof. Replays and expiry, including the `millis()` rollover case, are host-tested.

`tools/native_ota_strict_digest_probe.cpp` tests the exact pure C++ verifier with a real OpenSSL EVP SHA-256 adapter and only synthetic fixture username/password. The **actual ESP8266 BearSSL adapter, challenge response header, real browser SHA-256 compatibility, request-body streaming, private-AP transport and Digest account provisioning are not implemented or demonstrated**. This is separate from the OEM/SHINO RSA code-signing public key: HTTP Digest proves a temporary authenticated owner action, while firmware RSA proves package publisher integrity. Both and the manual intent gate must pass before any future writer can proceed. SHA-256 Digest on the isolated WPA2 AP is not a substitute for a cryptographically authenticated device or guaranteed TLS confidentiality; owner credentials must remain private and must not be put in GitHub, URLs or logs.

## Bounded real-stream transport model (HOST ONLY — NOT FIRMWARE SERVER)

`firmware/include/boot/NativeOtaStreamingReview.h` is the first composed streaming review contract. It joins previously standalone strict raw HTTP/1.1 headers, independently challenged SHA-256 Digest proof, explicit one-use manually approved consent, private-AP peer/signed-file identity and `IntentGate` transfer timing. It is **NOT included in the deployed FirstBootBridge or OEM rollback source**, and its output is exclusively a `ReviewSink` with no Updater/eboot/flash API. `BytesAcceptedForOfflineReviewOnly` is an informational state; it is **not** an OTA install decision.

- Raw header accumulation uses one **2,048-byte fixed buffer** and a 10-second total header deadline. It handles arbitrary TCP segmentation, including header terminator and first body bytes in the **same recv packet**, and never forwards payload to the host RAM sink before all independent host-claimed security inputs are checked. After successful strict Digest on the exact *raw* Authorization span (method/URI/nonce/peer bound), the request-envelope policy, manual approval token, declared transport size and `IntentGate` are checked in that order. The read-only browser GET cookie is not write authority. The fixed-length payload passes by externally supplied spans split at a maximum of **4,096 bytes**, with no firmware-sized staging buffer inside the gate. The mock host sink uses a vector **only in host tests**; it never executes flash operations.
- A streaming SHA-256 over **the entire selected signed transport**, separately from RSA verification and the OEM raw-image SHA-256, must equal the independently owner-confirmed selected file fingerprint. Wrong digest, missing bytes, extra/pipelined bytes, stage refusal, late EOF/finalization, digest/auth error, explicit disconnect or timeout permanently aborts the instance and discards host-only received bytes. `IntentGate` presently retains its existing **60-second overall arm lifetime and 15-second inactivity limit**, a deliberate conservative research rule that may require a separately reviewed real-world throughput policy. No automatic retry or checkpoint-resume. A successful exact byte-count completion remains noninstalling: the actual device trust anchor, signed package RSA verification, safe real flash staging and power-loss handling are still absent.
- `tools/native_ota_streaming_review_probe.cpp` compiles and executes the same C++ receiver with real OpenSSL SHA-256, a synthetic prechallenged Digest/manual owner confirmation fixture and a **RAM-only** review sink. It exercises 64,260-byte minimum and 494,404-byte upper-bound synthetic transfers, one-byte segmentation, split/combined header/body packets, short/extra body, changed byte, incorrect SHA, duplicate/malformed HTTP framing, wrong Digest/intent, failed/rejected sink, abort, timeout and replay. These are fabricated transport bytes, **not installable SHINO/OEM firmware**.
- `tools/native_ota_loopback_socket_probe.cpp` and `tools/test_native_ota_loopback_socket.py` additionally run the receiver on a **real POSIX TCP socket bound exclusively to 127.0.0.1 with an ephemeral port**, then send synthetic signed-length byte streams and adversarial requests through actual `send`/`recv`, varying fragmentation and HTTP request framing, including an actual TCP transfer of the full **494,404-byte synthetic upper-bound size**. This upper-bound fixture is **not** the real signed manufacturer application and does not verify RSA code signing. The temporary binary requires a controlled TCP write-half-close in this fixture before final review. Its `HTTP 200 OFFLINE_REVIEW_ONLY_NO_FLASH_OK` means solely that the host memory-review gate accepted the bytes; it never returns a device install acknowledgment. These tests do **not** exercise an ESP8266 network client, its memory pressure, a real browser `fetch`, private-AP isolation or real Digest challenge issuance.

## Native ESP8266 bounded client adapter — COMPILE ONLY; port 80 ownership BLOCKS activation

Source `firmware/include/boot/NativeOtaNetworkPump.h` now supplies a real ESP8266-`WiFiClient`-compatible cooperative reader for the previously host-tested streaming review. It owns only one **512-byte fixed read buffer** and performs at most **two reads / 1,024 bytes per firmware loop iteration**, with no heap-sized firmware body, socket listener, HTTP challenge endpoint or install side effect. The reader accepts independently prepared `NativeOtaStreamingReview` state, forwards exact raw TCP bytes, checks deadlines in idle polls, drains queued bytes even after TCP FIN, and refuses final byte acceptance until the peer has disconnected and the exact framing/fingerprint check succeeds. A partial or excess body, read error, explicit cancellation or timeout closes the borrowed client and irreversibly rejects the one-use review. This assumes an independently proven private-AP client and challenge/consent state: the pump deliberately **does not** invent those proofs.

`firmware/src/boot/NativeOtaDevicePumpCompileProbe.cpp` explicitly instantiates the SAME C++ streaming receiver and strict SHA-256 Digest logic with **real pinned ESP8266 WiFiClient and BearSSL br_sha256** primitives, plus a permanently denying review sink (`beginForReview() = false`). It declares no live instance/entry point, no `WiFiServer`, no port binding and is not referenced from `FirstBootBridge`. Its compile-time `SHINO_ENABLE_NATIVE_SIGNED_OTA == 0` check prohibits accidentally treating it as an enabled writer. The separate host g++ probe exercises cooperative read budgets, network fragmentation, full-size synthetic transport (494,404 bytes), TCP FIN after draining, short/extra data, read failures, idle timeout and one-shot cancellation. The earlier real 127.0.0.1 TCP tests remain a separate end-to-end HOST demonstration. **A compiled native type is not the same as running it on the unit or proving its real Wi-Fi memory/latency behavior.**

**Definitive port-80 integration finding:** `FirstBootBridge.cpp` currently owns `ESP8266WebServer server(80)` and calls `server.handleClient()` for the working browser UI, four-card LCD telemetry and Windows POST sender. Adding another `WiFiServer(80)` does **not** safely demultiplex connections; a buffered conventional `server.on(..., HTTP_POST)` loses the raw-header ambiguity assurances and risks an approximately 494-KiB String allocation. We therefore intentionally **do not wire this native pump into startup** or change the existing browser, AP configuration or legacy optional OEM return. A real nonwriting device listener first needs an independently reviewed, single-owner port-80 routing plan that forwards existing dashboard GETs, sessions and bounded metrics POSTs without behavioral regression, then selects the raw-OTA ingress *before* any buffered parser sees an upload. An alternative dedicated origin/port would require redesigning the strict Host/Origin policy and explicit browser/CSP/CORS interactions; it is not authorized as an implicit shortcut. Neither path has been claimed complete, and no on-device OTA POST is compiled.

The firmware writer, actual hardware CSPRNG challenge lifecycle, owner HA1 continuity, owner RSA signing public-key provisioning, app/FS geometry and real Updater failure/eboot handling remain independently blocked. No physical upgrade, factory return, device network connection or private image was requested or performed by this commit. **`permission_to_flash=false`; installed `review-002` unchanged.**

## Phase B: independent implementation and review gates (NOT DONE)

1. **Threat model / trust:** use the ESP8266 Arduino Core **built-in Signed OTA Update** (documented in core 3.1.2), not a hand-written signature protocol. The core supports `Update.installSignature(BearSSL::HashSHA256, BearSSL::SigningVerifier)`; its signed package format is `UNSIGNED_BIN || RSA_SIGNATURE || uint32_signature_length`, using SHA-256 / RSA verification. Embed ONLY an owner-selected signing **public** key; the corresponding private signing key is generated and backed up only on the owner's PC, never committed, logged, published as an artifact or placed in firmware. Sign via the pinned official ESP8266 core `tools/signing.py` and independently test unsigned, corrupted, wrong-key and correctly signed files using the EXACT core/toolchain pinned by PlatformIO. Add a separately authenticated bounded board/layout/version/size metadata check; valid signature alone cannot establish hardware compatibility or boot safety. Never equate caller-provided SHA-256 or Arduino Updater MD5 with release authentication. Reject unsigned/wrong-board/wrong-layout packages; a signer signing the wrong image could still brick the unit. Owner-private build credentials remain separate.
   - **Global Updater signature-state interaction:** `Update.installSignature()` acts on the shared core `Update` instance. Our optional exact-OEM return is an **unsigned, independently pinned** manufacturer app and cannot silently inherit native OTA's signature verifier. Review explicit signature-state initialization, separation and test coverage for both privileged writers before allowing either. Do not make a generic unsigned exception to native OTA. Losing the owner's private signing key prevents future native signed updates and must be addressed in a recovery plan.
   - References: [ESP8266 Arduino Core 3.1.2 OTA signed-update documentation](https://arduino-esp8266.readthedocs.io/en/stable/ota_updates/readme.html), [Updater.h signature hooks](https://github.com/esp8266/Arduino/blob/master/cores/esp8266/Updater.h).
2. **Exact runtime geometry:** observe actual `ESP.getFlashChipRealSize()`, `getSketchSize()`, `getFreeSketchSpace()`; check accepted app header, version/board/layout, rounded image length and at least one extra 4-KiB margin before any `Update.begin()`. Allow application `U_FLASH` only, never `U_FS`; fail closed on uncertain geometry.
3. **Authentication / CSRF / isolation:** existing read cookie must NEVER authorize update POST. Only separately authenticated privileged action, private-AP origin and one-use RAM authorization with short timeout, strict methods/content type/length, no redirects, no credentials in URL; protect session and stale-nonce behavior when telemetry sender is active. No user-facing automatic update.
4. **Transfer state machine:** IDLE→AUTHORIZED→STREAMING→DIGEST_VERIFIED→STAGED→CONTROLLED_RESTART; all unexpected requests, chunk overrun, client disconnect, timeout, mismatched MD5/SHA-256, early EOF, duplicate POST and power-cut experiments must fail closed. Streaming with bounded RAM; compute SHA-256 incrementally, do not trust supplied checksum. Ensure incomplete writes cannot call `Update.end(true)`; investigate and verify Updater cancellation semantics and how staging/eboot behave on each failure.
5. **Testing:** unit/parser/fuzzer fixtures, full microcontroller compile (normal + owner experimental return modes), flash footprint and no-FS checks, simulated malformed/dropped/duplicated chunks, interrupted sessions, simultaneous browser polling and Windows POST. Independent code review of every write route, read-session privilege isolation, and no unexpected recovery endpoint. CI must publish neither flashable firmware nor credentials.
6. **Recovery and user instructions:** demonstrate complete owner-specific safe restore possibilities separately (no claim if none), document power-loss limits, maintain `review-001` and `review-002` immutable; owner must separately authorize the exact first OTA of a future signed writer version. A nonbooting application cannot guarantee Web-based rescue. Shipping needs real-device monitored confirmation and later one deliberately approved SHINO→SHINO test, without any scripted retry.
