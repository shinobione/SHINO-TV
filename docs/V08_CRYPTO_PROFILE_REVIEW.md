# SHINO // TV V0.8 Mission 1 — media-only crypto profile candidate

**Status: standards-based host research, not production authentication.** The candidate uses [RFC 9421 HTTP Message Signatures](https://www.rfc-editor.org/rfc/rfc9421.html), [RFC 9530 Content-Digest](https://www.rfc-editor.org/rfc/rfc9530.html), and [RFC 8941 Structured Fields](https://www.rfc-editor.org/rfc/rfc8941.html). RFC 9421 supplies signature mechanics; application authorization, replay handling, key lifecycle and framing are this proposed profile's responsibilities. The host lab verifies real ECDSA-P256-SHA256 signatures with Node crypto over fixed public vectors. It is a narrow profile parser, **not** a complete RFC 8941 implementation or an ESP8266 verifier.

## Exact covered message and signature base

Only HTTP/1.1 origin-form `POST` is eligible. Require one `Signature-Input` dictionary member and one matching `Signature` dictionary member, both named `sig1`. The covered component identifiers, in this exact order, are `"@method"`, `"@request-target"`, `"@authority"`, `"content-type"`, `"content-length"`, `"content-digest"`. No component identifier parameters are allowed. The derived values come from the bounded ingress owner's actual method, raw request target and single Host authority; field values come from uniquely parsed raw headers. Reject duplicate fields even if their values match. This is a narrower transport profile than general HTTP field combination and narrower than RFC 8941's full grammar.

The `Signature-Input` Inner List has exactly four parameters in fixed order: `alg="ecdsa-p256-sha256"`, `keyid="<media-key-id>"`, `nonce="<challenge>"`, `tag="shino-tv-media-v2"`. The lab bounds the key ID to 1–24 lowercase ASCII letters, digits, underscore or hyphen, and the challenge to 22 unpadded base64url characters representing a proposed 16-byte value. The exact signature base follows RFC 9421 Section 2.5: one `"<component>": <value>` line per covered component, LF separators, then `"@signature-params": <canonical Inner List>` with no final LF. The `sig1=` dictionary label is **not** part of the last base line. The fixed Begin vector's base is:

```text
"@method": POST
"@request-target": /api/v2/bridge/media/begin/11223344556677880000000000000001
"@authority": tv.test
"content-type": application/vnd.shino-tv.media-wire-v2
"content-length": 371
"content-digest": sha-256=:m089HfUsWQVYMPNG1o0KJrdGc9c1liLjlhvkCDadGH4=:
"@signature-params": ("@method" "@request-target" "@authority" "content-type" "content-length" "content-digest");alg="ecdsa-p256-sha256";keyid="media-test";nonce="AAAAAAAAAAAAAAAAAAAAAA";tag="shino-tv-media-v2"
```

The LF-delimited bytes, not a pretty-printed representation, are SHA-256 hashed for ECDSA verification. RFC 9421 Section 3.3.4 defines the signature output as exactly 64 bytes: unsigned big-endian 32-byte `r` followed by 32-byte `s`. `Signature: sig1=:<canonical base64 of 64 bytes>:` is an RFC 8941 Dictionary with a Byte Sequence value. Node's `ieee-p1363` encoding supplies/verifies that representation. ECDSA signing is nondeterministic; tests verify fixed signatures, never re-sign and compare bytes. The vector file contains **only a public test key**, fixed signatures, bodies and signature-base hashes. Its one-shot generated signing key was discarded. The fixed challenges and `tv.test` are public test data, not deployable credentials, epoch issuance or origin identity.

`Content-Digest` is exactly one `sha-256` Dictionary member with one 32-byte canonical base64 Byte Sequence, e.g. `sha-256=:...=:`. It hashes the entire request content: the 40-byte v2 header followed by its 0–512 payload bytes. Before body read, the signature authenticates the **declaration** of those bytes. After body read, independently recompute SHA-256 and compare in constant time before interpreting metadata, revoking old art, writing a tile or publishing Commit. RFC 9530 explicitly does not make a digest alone an authentication mechanism. The wire CRC32 and final whole-cover SHA-256 remain separate integrity checks with no principal authority.

The host lab's grammar accepts only the exact fixed-order `Signature-Input` and one exact `Signature`; it rejects duplicate dictionary labels/parameters, unknown or reordered parameters, alternate algorithm, invalid byte-sequence encoding and extra members. A production implementation must either use an independently reviewed RFC 8941 parser with an equally strict post-parse policy, or prove this constrained grammar is complete for every accepted input and interop peer. The host regex is **not** that review. RFC 9421 notes that `@request-target` is difficult to reconstruct outside HTTP/1.1; this profile rejects any other version. There is no `created` or `expires` parameter because the device has no established trusted wall clock; the monotonic server challenge lifetime is the replay gate instead. A future time-source decision could change that profile only after new vectors and review.

## Principal, key and challenge lifecycle candidate

A provisioned public-key entry would map one `keyid` to one media-only principal, an allowed operation set and a revocation state. No browser cookie, existing Basic/Digest fallback, OTA credential, OEM authority, `track_key`, CRC, image SHA or model `Authority` object may satisfy Gate 1. Gate 1 must verify the actual signed method/target, key role, current epoch and single-use challenge **before body consumption**. A signed `commit` target cannot inherit `begin` authority. A wrong or revoked key cannot mutate another principal's pending transfer. The V0.7 transaction sequence high-water is an additional bounded state-consistency check, not nonce freshness.

Proposed issuance rules for further review: at successful boot, derive a new nonzero 64-bit wire epoch from an approved cryptographic randomness source and fail closed if freshness cannot be established. The epoch is copied into the first eight bytes of every 16-byte transaction and into binary bytes 8–15. Independently issue a 128-bit unpredictable challenge for a particular media key and current epoch, with an absolute monotonic expiry. Maintain a fixed per-key outstanding slot count; fail closed at capacity and never evict a live slot to admit another. An independent sweep can reclaim only expired slots. Atomically consume the challenge after full Gate 1 signature/role/epoch proof and **before** any body byte. A body failure burns the challenge. Reboot, key revocation or boot epoch replacement invalidates all slots. Reject unknown, used or expired challenges, including at the exact deadline. A failed signature must not consume a valid slot. Host tests use two slots per key as a fixture, not a production sizing decision.

Challenges must be issued through a separately reviewed bounded path with rate limiting and key binding. That path, its pre-authorization, transport confidentiality, replay/DoS properties and sender round-trip cost for nine tiles are unresolved. A 64-bit random epoch has a nonzero collision probability and cannot alone prove reboot freshness; entropy health, failure behavior and any persistent monotonic supplement need review. A captured signed request that wins the race to consume its challenge can deny the legitimate sender even though it cannot forge a different body. HTTP signatures give no confidentiality over local HTTP.

Public-key enrollment/rotation/revocation needs an owner-approved auditable process, durable media-only role mapping and a key-compromise response. No production private key, secret, credential, signing endpoint or device public-key store is implemented here. The PC private-key custody design and the exact BearSSL/P-256 verifier implementation, canonicalization library, native cost and side-channel review remain open. Public test vectors must never be mistaken for production provisioning.

## Host evidence and security limits

`tools/v08_crypto_vectors.json` fixes seven signed requests: valid Begin/Tile/Commit, operation/transaction/epoch body disagreement, and an independently signed wrong-key-id request. `tools/test_v08_crypto_lab.js` verifies the fixed base SHA-256 values and real signatures, strict field/target rejection, no body reads or body allocation for denied Gate 1 cases, role denial, stale epoch, exact challenge expiry, replay, bounded challenge capacity, changed/partial/trailing body, and Gate 2 agreement. `tools/test_v08_vector_compat.py` checks valid binary records, canonical metadata and digest bytes against the unchanged V0.7 host reference. A valid signed digest declaration with a conflicting binary record reaches Gate 2 and fails there. This matters because signature validity does not imply that the declared body was actually sent.

Node crypto, fixed test buffers and a small constrained parser do not qualify target cryptography, key storage, entropy, HTTP framing, parser interoperability, constant-time error handling, heap/stack use, loop fairness or physical behavior. The host stream already holds complete bytes and cannot prove that a native TCP layer does not read ahead. The review remains **HOLD** for an unconnected native verifier and **BLOCKED** for production authorization.
